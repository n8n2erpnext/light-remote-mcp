## Wall realtime fix

The apparent multi-job delay was a browser-side Wall problem, not executor/SSE transport latency.

The old UI could issue many concurrent `/api/sessions` refreshes while replaying session history, rebuild a whole job card on every stdout chunk, repeatedly scan every job for filtering, and race history replay against live SSE without deduplication.

Current safeguards in `gateway/dashboard.mjs`:

- deduplicate history/SSE/reconnect events using event ID + timestamp
- debounce/single-flight session metadata refresh
- no fixed full-session polling loop
- batch DOM render updates at 75 ms
- avoid building large filter haystacks unless a filter is actually present
- SSE remains primary
- one lightweight `/api/activity?limit=1` probe per second detects a missed event
- catch-up fetch runs only when the head probe sees an unseen event
- probe stops while document is hidden or Wall is paused

Measured source/gateway SSE events were about 1–4 ms after rebuild. The one-second probe is only a fallback and is not a session heartbeat.

`deploy/scripts/selftest-wall.mjs` now pins the realtime safeguards and rejects restoration of fixed full-session polling.

## Transport limitation captured for v0.6+

Current Vercel `/api/operator` uses GET/query/base64 as development bootstrap transport. It is acceptable for small calls but has already failed on large source patches with malformed/truncated base64.

Do not carry this transport design into the public product. Use body-safe Streamable HTTP/POST (or equivalent) for large source/tool payloads. During current soak, use RDC only as rescue for oversized patches or self-disruptive rebuild/restart steps.
