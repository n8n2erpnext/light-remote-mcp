## 2026-11-04 ~21:45 ICT — Encrypted OFFLINE CA backup and isolated signer recovery drill (SOURCE PASS, no real CA)

New source `deploy/scripts/gold-abv2-mtls-offline-ca-recovery.mjs` supports **two explicit, locally invoked operations**. It is intended to run **only on an Owner-controlled OFFLINE signing computer**, not on VPS-ARM, LXD Lab, Plugin, Traefik, CI or any network-exposed runtime. Only disposable CA fixtures were used during development. It does not create a CA, install credentials, schedule backups, contact networks or select an Owner's real backup media.

- `backup`: checks an existing self-signed CA certificate and matching private key in a 0700 signer directory with key file 0600; writes a *separate* 0700 backup directory containing only public `ca.crt`, encrypted `ca.key.pk8` (PBES2 AES-256-CBC/PBKDF2-HMAC-SHA256, 600,000 iterations), and non-secret `ca-backup.json` identity/integrity manifest. It refuses overwriting existing backup, insecure paths or weak/unsafe passphrase files. No plaintext key is intentionally written to backup.
- `restore`: from encrypted backup into a *different, empty* 0700 recovery directory. It checks manifest/CA fingerprint and encrypted key hash, requires an independent private 0600 passphrase file, decrypts and matches restored signing key to public CA. Any error removes newly-created partial recovery files. Neither the passphrase nor PEM/key bytes are written to stdout, logs, checkpoints or Git.
- **Passphrase custody:** Owner personally generates a high-entropy passphrase, saves it in a separate private file outside source/backup/recovery directories and retains an independent offline recovery method. A 24-byte minimum file-size check is only a weak-input guard, **not** a proof of entropy. Never transmit the passphrase or encrypted CA private key to an AI agent, GitHub or a public VPS. Private archive and key custody must be separately approved.
- **Integrity and trust:** the SHA-256 values in `ca-backup.json` are an accidental-corruption check, not an authenticated signature against an attacker replacing the entire backup. **Restore requires a separate `--expected-ca-sha256` pin independently recorded by the Owner** and fails closed if it does not match the archive's public CA identity. After restore, it also verifies the private key matches the pinned CA public certificate; the disposable CSR signing drill proves usable recovery. This workflow does not establish key non-exfiltration, secure erase, storage encryption at rest, or a formally approved disaster-recovery policy.

Owner-side commands, **examples only, do not run on the connected VPS**:

```sh

node deploy/scripts/gold-abv2-mtls-offline-ca-recovery.mjs restore --backup-dir /offline-owner/encrypted-backup --restore-dir /offline-owner/isolated-rehearsal --pass-file /offline-owner/independent-secret/passphrase --expected-ca-sha256 <INDEPENDENTLY_VERIFIED_CA_CERT_SHA256>
```
