# Gold PostgreSQL / Redis connection and Notification persistence — 2026-10-17

## What was added

- `platform-v2/src/storage/gold-data-plane.mjs`: real Node `pg` and `redis` clients, accepting only independently scoped Gold credentials from 0600 files; PostgreSQL database must be `light_remote_gold_dev`, non-superuser application role `lr_gold_app`. Checks exact 1..13 installed migration versions, Redis PING and an isolated TTL/NX/read/delete probe. If either backend fails, it closes connections and throws; **no JSON or Redis-to-in-memory fallback**.
- `platform-v2/src/storage/notifications-pg.mjs`: replacement of JSON-file notification persistence using the existing RC.50 `lr_notifications` / `lr_notification_reads` schema, parameterized inserts/queries, recipient/plan/group audience filters, atomic mark-read idempotency and no file-backed storage.
- Existing `operator-host/executor-routes-account.mjs` now awaits Notification repository methods, maintaining compatibility with legacy synchronous test repositories and asynchronous PostgreSQL storage.
- Operator now supports an **explicit development-only opt-in**, `LR_GOLD_NOTIFICATIONS_PG=1`, that opens verified Gold PostgreSQL/Redis connections and instantiates `GoldPgNotificationRepository` before opening its socket. Missing credentials, wrong database/role/schema, or Redis failure abort startup rather than silently falling back to JSON. No other domain switches to PostgreSQL through this flag.
- `deploy/scripts/selftest-gold-notification-pg-mode.mjs` proves fail-closed startup without the independent authorization/configuration and validates every awaited route. `deploy/scripts/probe-gold-data-plane.mjs` is a credential-redacted operator-owned live connection probe; it is **not yet runnable** against actual Gold DB until legitimately provisioned.
- `platform-v2/test/gold-data-plane.test.mjs` adds unit tests for database identity, role, schema versions, credential file permissions, Redis readiness/namespace and cleanup, connection failure, and PostgreSQL notification contract.

## Migration 016 — Support ticket outbox as a transactional PostgreSQL queue

- Added **Gold-only** `016_support_outbox.sql`, SHA-256 locked after unchanged migrations 001..015. PostgreSQL table `lr_support_outbox` stores account-scoped ticket payload and delivery status, lease owner token/expiry/type, next retry and remote ERPNext processing status. `payload` is native PostgreSQL JSONB **inside the database**, not a standalone JSON file or separate SQLite database.
- `platform-v2/src/storage/support-outbox-pg.mjs` implements transactional, idempotent enqueue with an advisory transaction lock for global pending capacity; account-specific event status; `FOR UPDATE SKIP LOCKED` delivery and remote-status leases; lease-token/fencing checks before acknowledgement, backoff and remote-status changes. A stale worker cannot overwrite a newer owner. These controls depend on live PostgreSQL transactional semantics that are **not yet tested on a real Gold DB**.
- Opt-in `LR_GOLD_SUPPORT_OUTBOX_PG=1` in Plugin opens verified Gold PG/Redis before HTTP listening, shares that pool with Site Announcements and Analytics, and injects `GoldPgSupportOutbox` instead of instantiating the legacy JSON-backed `SupportOutbox`. Support GET status and POST submit route both await the data-layer operations; same-origin, account auth, Pro/VIP plan, sanitized form and rate gates are retained.
- **External ERPNext dispatch stays deliberately disabled.** While no approved sender is wired, Support POST returns `503 support_delivery_not_ready` instead of falsely acknowledging a ticket; the Gold worker timer is skipped. Attempting `LR_GOLD_SUPPORT_DELIVERY_ENABLED=1` aborts Plugin startup rather than contacting ERPNext. Synthetic delivery callbacks are tested in isolation only.
- Seven new Support repository tests exercise accepted PostgreSQL enqueue, idempotency, cross-account isolation, Free-plan denial, lease competition, stale-lease fencing, retry/backoff, status polling and synthetic send/ack. Three plugin integration tests verify source wiring, startup fail-closed and external delivery prohibition. Production's legacy SupportOutbox behavior is unchanged.
- **Exactly-once caveat:** A PostgreSQL lease prevents concurrent sends; a process crash after ERPNext receives an HTTP request but before PostgreSQL commits the acknowledgement can result in a retry. Remote exactly-once delivery requires independent verification that ERPNext deduplicates the stable `payload.event_id`. Frontend HTTP retry idempotency also needs persistent client-generated event IDs before Gold can be declared complete.
- These changes have not been exercised against PostgreSQL 17 / Redis 8 running on the Gold host. Other Operator/Plugin JSON-backed registries remain to migrate. **Gold is not a functioning all-PG release**.

## 2026-10-17 canonical Operator notification canary correction
