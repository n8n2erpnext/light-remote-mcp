## Current source progress
- `lib/gold-connection-job-reaper.mjs` now performs a SECOND PostgreSQL latest-connection and device-presence read after its cleanup writes, checking changed connection generation, heartbeat state and offline eligibility, plus final signed channel freshness. A concurrently detected reconnect ROLLBACKs the entire cleanup. This is an additional protection, NOT proof of multi-Operator serializable epoch ordering.
- `deploy/scripts/selftest-gold-connection-gc-races.mjs` mock-injects a second connection, new heartbeat and late signed channel; all cause rollback, while steady offline state commits. No real PG concurrency claim.
- `lib/gold-reconnect-proof.mjs`: standalone bounded Ed25519 source protocol: canonical JSON, account/device identity, random challenge, signed inventory, captured-time freshness, 64-bit monotonic epoch validation, bounded unique job/process records and fail-closed decision. Signed inventory alone NEVER resolves a no-PID/resource-unknown fence; exact authentic terminal ACK still required for PID fences. `selftest-gold-reconnect-proof.mjs` tests tampering, replay, old epoch, cross-device mismatch and no false ACK.
- CI workflow `gold-connection-lifecycle-gc.yml` uses branch-specific source tests, no production release jobs.

## Important NOT YET IMPLEMENTED — mandatory before migration 040 activation
1. **Server issue**: a durable per-device PG execution epoch counter, serialized with GC and M4 admission (likely new additive migration 041; do NOT rewrite already locked migration 040). Handshake must issue challenge + committed epoch, bind to A/B-authorized enrolled device key and account/device/connection generation. Renewals/reconnects cannot roll epoch backwards; restart and multiple Operators must not reset it.
2. **Agent persist/fence**: fsync current accepted epoch and any prior outstanding commands in local private journal BEFORE acknowledging epoch change; reject every OS-effectful command from an older/unknown epoch before spawning. Epoch must be conveyed in ALL Fleet command transports including poll and duplex, with signed server authority, not trusted from user request fields. Duplicate replay must return authentic prior result or explicit UNKNOWN, never launch twice.
3. **Inventory**: enumerate all live managed processes and durable supervisor/command journal rows (not only `listDevice` last 64), with exact jobId, operationId, processId, native PID, start identity and terminal spool; pagination/completeness proof must be bounded and overflow fail closed. Link jobId to Agent commandId/operationId when writing the local journal BEFORE dispatch. Protect from PID reuse and truncated/aged-out journals.
4. **PG reconciliation**: atomically compare signed device proof with authoritative pending GC fences and prior epoch under M4 device advisory lock and account identity, then resolve only exact verified signed terminal receipts or a separately designed fsynced zero-dispatch certificate. A missing process in a signed snapshot, OS boot timestamp, new epoch, or online channel alone is NOT sufficient to clear a fence.
5. **Races**: real disposable PostgreSQL race tests for GC vs reconnect/new admission/late receipt, two Operator instances, stale Redis heartbeat, PID reuse and failing journal, plus restart/load tests and durable ACK/audit idempotence. A single-instance mock PASS is not enough.

## Additional controlled-scope safety after first CI green
The previous unscoped reaper would sweep the real historical unrelated claim as soon as the global worker was enabled. A strictly optional `OPERATOR_CONNECTION_JOB_GC_ONLY_DEVICE_IDS` comma-separated allowlist is now parsed by Operator and passed into Reaper; SQL candidate enumeration and direct `sweepDevice` are both constrained. Configuring an invalid or empty list fails startup instead of inadvertently widening the sweep. In a future single-device UAT activation, explicitly set this to the exact **new synthetic test device ID**, never to a broad active customer list. Omission keeps intended future account-wide production semantics; worker remains OFF by default. This is a source-only control and must still undergo a Gold UAT owner-approved staged rollout.
