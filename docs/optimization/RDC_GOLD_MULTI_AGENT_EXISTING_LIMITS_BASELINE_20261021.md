### Actual architectural limits confirmed by source + isolated in-memory test
- `operator-host/session-manager.mjs`: one reusable session lane per `accountId/deviceId/agentId`. `hold` sessions **still count** against session capacity. `SessionRegistry.maxActive` default **5** globally, with `maxActiveForNode` from Agent default **2**. Synthetic in-memory test PASS: two distinct test Agent session identities on a node allowed, third received `node_session_capacity_reached` HTTP 429; five sessions across multiple synthetic nodes allowed, sixth received `session_capacity_reached` HTTP 429; re-opening same identity returned existing session. **This is in-memory source regression evidence, not three separately paired live agents.**
- `operator-host/executor.mjs` `PLAN_FEATURES`: Free has `toolCallLimit=10_000`, Pro/VIP have no monthly tool-call limit; Fleet Wall and multi-device console features differ. There is **NO per-plan 1/3 concurrent Agent execution entitlement** in current `planEntitlements`; session ceilings and Team seats are not equivalent to active execution slots. Source `operator-host/pro-team-registry.mjs` `MAX_SEATS=5` requires separate Team entitlement and does not implement the requested per-account 1/3 Agent scheduler.
- `operator-host/fleet-router.mjs`: node queue exists, default `maxQueuedPerNode=64`, command lease 12s, fresh channel TTL 20s. Serialized polling yields `queued` rather than actual two-command parallel execution on Linux; Windows pre-patch pulse incorrectly sent `draining:true` while executing work, causing 409.
- `device-agent/operator-agent.mjs`: Linux daemon at Gold `eee3a6b` now calls signed `/device-channel/pulse` with actual owner drain state; prior Windows `6729f5d` still sends signed `poll` with `draining:true` while running a command. **Do not treat busy as user-requested maintenance drain**.
- `lib/native-process.mjs`: default **16** live managed processes per Agent (`maxProcesses` constructor), runtime ceiling tunable up to 64 if caller opts in; default per-stream output ring 4 MiB (max 16 MiB), process result retention 6h. Process timeout can reach 24h; command `light_remote_exec` tool's input timeout caps at 2h. The agent-side process registry remains **in-memory**: shutdown `close()` stops child process trees, so a managed process is not yet a durable, recoverable background download/build job across Agent restarts.
- `plugin-server/tools.mjs` offers explicit process stop / terminal stop, but currently no dedicated owner-authorized **`exec` cancel** operation. An `exec` can time out, but timeout is not an interactive cancel button. Windows `force:false` currently reaches `taskkill /T /F`; cannot promise graceful cancellation on Windows today.
- Native managed process *concurrency* does not prove *multi-Agent admission* or safe same-project concurrency. No existing resource-lock scheduler for build/project/desktop ownership or fair per-Agent queues was demonstrated by these tests.

## Boundaries, unresolved acceptance and proposed next engineering gate
1. **Do not claim Free (1 active Agent) or Pro (3 simultaneous Agents) is implemented or physically accepted.** Both currently approved Gold leaves are on Pro and this MCP client represents one Agent identity. Owner must authorize separate real Agent principals before actual 3-way physical tests; do not spoof identities on live service.
2. New Gold Windows `eee3a6b` installer CI previously passed, but physical Windows install/after-test was deliberately postponed at the owner's request. Distinguish existing old-Agent drain bug from Linux new-Agent correct queue behavior.
3. Need explicit **account-scoped Agent admission tokens** with Free=1 / Pro+ =3, plus per-device capacity and fair queued work; don't abuse `sessionCeiling` or set drain to represent occupied slot.
4. Need **separate managed durable background job** policy for transfer/download/build with resource budgets, ownership, verified progress, cancel (soft vs force semantics), recovery after restart and clear partial-artifact handling; do not pretend the current per-Agent in-memory process registry is durable.
5. Resource locks/CAS scoped to project/file/build/package-manager/desktop and account-device-session ownership are required before three Agents mutate shared resources concurrently. Side-effect ambiguity remains non-retryable after restart.
6. Future acceptance should re-run the same A/B busy-overlap on Windows AFTER installing the new approved Gold Agent, then test Free queueing and three independently authorized Pro Agent identities. Avoid synthetic workload inflation or production rollout without explicit owner choice.

**Baseline conclusion:** Gold already supports multiple independent OS processes inside a single authorized Agent, but current `exec` dispatch is serial and old Windows can spuriously DRAIN. There is no demonstrated plan-aware multi-Agent scheduler; native process slots, sessions, Team seats and Agent slots must remain distinct.
