## Product model locked in this session

The architecture is no longer ambiguous. Keep these invariants:

- `Light Remote Service` is an always-alive local OS service. Terminal/browser lifetime does not own it.
- `Device Connection Lease` is the finite cloud connection: Free ~4h, Pro 24h, VIP 72h; no Unlimited. It ends only on explicit Disconnect/revoke/authority failure/hard expiry.
- **15–60 minute idle/reconnect grace does not close Device Connection.** It belongs to Agent/access lifetime.
- `Device Access Grant` is per exact `deviceId + connectionId`; it may cover multiple Agent lanes on that device.
- `Agent Session` is keyed by `(deviceId, agentId)` and has `ACTIVE/HOLD/CLOSED/EXPIRED` semantics. Temporary transport loss may HOLD/resume inside grace.
- Hard Device Connection expiry cascades and closes child grant/sessions. Agent idle does not close the parent Device Connection.
- Wall is strictly **observer/control surface**, not keepalive/session host. Closing/reloading/browser loss must not affect service, connection lease, grant, Agent session or durable job.
- Standard user Wall = current operator Wall UX scoped to exactly **one device**. VIP Wall = same concept aggregated across N devices.
- A normal user watching two devices opens two device Wall tabs/windows. VIP is convenience aggregation, not stronger authority.

Canonical hierarchy:
```text
Account / transitional owner identity
  -> Device Identity
  -> Device Connection Lease
  -> Device Access Grant
  -> Agent Session A/B/C...
Wall reads/controls this state but does not own its lifetime.
```

## P4.5 A/B pairing — canonical security/UX model

This replaces pre-auth device enumeration as the **public golden path**.

- **A code** = device discovery/pairing challenge generated by the exact Local Wall.
- A is short-lived (target 2–5 min), one-time, rotated on Wall visit/reload/New A, and bound to current `deviceId + connectionId`.
- Server stores only verifier/hash where practical. A plaintext must not be emitted into activity/audit after issuance.
- User gives A to ChatGPT/Codex/Claude. If A is supplied, Agent calls high-level `connect(A)` immediately.
- Redeeming A resolves the exact device and consumes A immediately. **A alone never grants execution authority.**
- **B code** = access approval challenge created after A redemption, bound to exact request + device + connection.
- Server returns B plus opaque continuation to Agent. User enters B at that exact device `/approve` and explicitly Approves/Deny.
- Even if an underlying Device Access Grant already exists, a new A/B pairing must still require B approval; leaked A must never bypass owner confirmation.
- Wrong-device B approval, A replay, expired A/B, connection change and disconnect must fail closed.

The analogy is intentionally similar to two-sided 2FA/challenge-response: possession of only A or only B is insufficient. The owner must control the Wall and explicitly approve B.
## Agent-facing contract — keep bootstrap tiny

The whole reason for P4.5 is to avoid wasting ChatGPT/Codex tokens on discovery. Normal Agent state machine:
```text
need_a_code
  -> connect(A)
approval_required + B + opaque continuation
  -> owner approves B on Wall
ready + device + opaque client
  -> list-devices / session / exec / job / output
```

Hard rule: if user supplies A, **do not call** `devices-bootstrap`, fleet, capabilities, account lookup or broad status probes first. Those are compatibility/debug/admin surfaces only.

Target compact response shapes:
```json
{"status":"approval_required","code":"<B>","continuation":"<opaque>"}
{"status":"ready","device":"VPS-AMD","client":"<opaque>"}
```
Continuation/client values are bearer-like capability material: keep them private; never quote them back to user or log them.

After first approved device, the same Agent client may A/B-pair more devices independently. `list-devices(client)` returns only that client's currently authorized device set, **not account inventory**. If one authorized device exists, unqualified work may route there. If several exist and target is ambiguous, ask which authorized device. Explicit Task A on Device A + Task B on Device B may run concurrently.

## Security hardening added before live A/B acceptance

Security review found a critical gap: `amdwall.thaiduy.store` was publicly reachable through reverse proxy while Local Wall originally assumed loopback/private access. A/B would be bypassable if an attacker could open the public Wall, obtain A, receive B and approve it themselves.

This was fixed before P4.5 live acceptance:
- Loopback Wall may run without device-local auth.
- Any non-loopback/private/VPN bind **fails closed unless device-local Wall auth is configured**.
- Auth protects root, A-code issuance, `/approve`, APIs, SSE, Connect/Disconnect and future policy/maintenance controls.
- Password verifier uses scrypt; stored config is mode `0600`.
- Wall session cookie is signed, HttpOnly, SameSite=Strict, Secure when reverse-proxy request is HTTPS.
- Login throttling and mutation-origin/Fetch-Metadata CSRF checks are present.
- Reverse proxy/TLS/NetBird are outer transport defenses, not substitutes for Wall owner authentication.
- `wall-auth-init` reads password from stdin, not argv, and does not echo it.

Transition decision from owner: Device Walls currently use username `operator` and the same password as hosted Wall for UX consistency. Cookie-signing secret remains unique per Wall/device. P5 account registration/login replaces this shared transitional login later.
