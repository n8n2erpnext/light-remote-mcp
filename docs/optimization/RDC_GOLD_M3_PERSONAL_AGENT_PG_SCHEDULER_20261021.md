# Gold M3 — Personal Agent PostgreSQL Scheduler (first executable slice)

**Date:** 2026-10-21. **Plan:** [Multi-Agent / Job Scheduler Master](./RDC_GOLD_MULTI_AGENT_JOB_SCHEDULER_MASTER_PLAN_20261021.md) and [mandatory Pro Team compatibility](./RDC_GOLD_MULTI_AGENT_PRO_TEAM_COMPATIBILITY_20261021.md). **M5 baseline:** [isolated workers accepted](./RDC_GOLD_M5_ISOLATED_SYSTEMD_WORKER_20261021.md).

## Contract and scope
Free **2 retained sessions / 1 executing authenticated Agent**, Pro/VIP **12 retained sessions / 3 executing Agents**. Retained HOLD sessions do **not** use Agent execution slots. Agent identities are taken from the already validated session, never a free-standing submitted label. Queue reason is `QUEUED_AGENT_SLOT`, distinct from `target_node_draining` (maintenance/owner drain). This first slice is deliberately **foreground exec only**, behind `OPERATOR_PERSONAL_AGENT_SCHEDULER=1` (OFF by default), and requires existing `OPERATOR_SCOPED_SESSION_LIMITS=1`. Background process launch M2/M5 remains separately bounded and other tool families need a later Scheduler gate. Do not claim complete multi-tool Agent scheduler from this first slice.

## Canonical relational data / migrations
- `platform-v2/sql/032_gold_personal_agent_admission.sql`: typed `lr_gold_personal_agent_work` with job/account/Agent/session/operation IDs, explicit queued/running/finished/unknown states, timestamps, disposition, constrained indexes and unique account+operation; no command scripts, credential data or JSONB job snapshots in scheduler table.
- `GoldPersonalAgentScheduler` uses PostgreSQL advisory transaction lock per account to admit at most Free 1 or Pro 3 *distinct Agent IDs* concurrently; exactly one in-flight foreground job per Agent to prevent flooding. Waiting Agent jobs stay in SQL queue, with earliest queued eligible Agent winning freed capacity; no false device drain and no invented ETA.
- `GoldJobLedger` records `queued` in the same canonical PG job table and preserves G4 operation reservation-before-effect. Migration changes the job-status CHECK to include `queued`, leaving existing terminal statuses intact. App role receives only scoped DML privileges, not schema CREATE or migration rights. Manifest/config now require 32 migrations; **do not cut over new source before isolated Gold migration 032 is applied with independent migrator**.
- `operator-host/executor.mjs` reroutes foreground `exec` through an opt-in queue controller. It rechecks session state, device binding, account entitlement and capabilities immediately before dispatch. When job is terminal, the account slot is released in PG, then next eligible Agent admitted; background worker's continuing process does not occupy foreground slot after launch.
- `GoldPersonalAgentScheduler.recoverStartup` converts abandoned queued/running records to `unknown` without replaying scripts. Operator holds only pending closures in memory; PostgreSQL holds canonical admission/operation metadata. Team actor/billing/seat flow unchanged and cross-account Team execution remains OFF.

## Safety
No privilege elevation, no relaxed device capabilities or A/B policy, no billing/Team change. Rollback boundary: disable `OPERATOR_PERSONAL_AGENT_SCHEDULER`, leave typed SQL table and completed G4 tombstones in place; source restore via verified LXD backup. Migration 032 is additive except job-status CHECK extension and must be applied with verified migration SHA and separate migrator, never by app role.
