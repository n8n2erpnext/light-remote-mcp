# Gold M5 — Isolated per-job systemd user workers (Linux UAT, first slice)

**Date:** 2026-10-21. **Depends on:** [Gold M5 Supervisor and Agent-restart acceptance](./RDC_GOLD_M5_INDEPENDENT_PROCESS_SUPERVISOR_20261021.md), [Supervisor crash journal and UNKNOWN reconciliation](./RDC_GOLD_M5_SUPERVISOR_RESTART_RECONCILIATION_20261021.md), [full Multi-Agent plan](./RDC_GOLD_MULTI_AGENT_JOB_SCHEDULER_MASTER_PLAN_20261021.md).

## Core implementation and scope
Previous Supervisor lived in a systemd **system** cgroup with `KillMode=control-group`. Jobs spawned there were terminated when Supervisor stopped. We verified `gold-uat` initially had **no systemd user manager**; an isolated UAT `loginctl enable-linger gold-uat` enabled `user@999.service` and a private `/run/user/999` bus. A bounded temporary `systemd-run --user` service was proven to stay active across real Supervisor restart and was then stopped/cleaned. Neither `setsid` nor PID-only journaling is accepted as process survival.

This optional backend is enabled **only** when `LIGHT_REMOTE_PROCESS_SUPERVISOR_ISOLATED_WORKERS=1` is explicitly set on a Linux Supervisor that already has the **owner-only fsynced journal** configured and a usable independent user systemd manager. It is OFF by default, and must never auto-enable on Windows/macOS or on unsupported hosts.

New source components:
- `device-agent/isolated-process-worker.mjs`: each non-interactive job runs in its own `systemd-run --user` transient service/cgroup, owns its shell child process, persists bounded stdout/stderr (up to 4 MiB each) and an fsynced final OS exit receipt. The launch request file (which may include a signed download URL or other secrets) is `0600` inside a `0700` job directory and deleted before command spawn. Output files and status are `0600`. OS timeout and stop are enforced; no automatic service restart/re-execution.
- `lib/isolated-worker-manager.mjs`: uses explicit argv `systemd-run --user`/ `systemctl --user`, no shell templating. Checks the observed user-unit **ControlGroup** and `/proc/<mainPID>/cgroup` before claiming `running`. If unit is gone without a fsynced terminal receipt, returns `unknown`; does not infer running from a stale PID. Provides persistent bounded stdout queries and per-unit Stop/Force Stop.
- `device-agent/process-supervisor.mjs`: routes only `executionMode='background'` jobs through isolated workers when enabled; interactive `light_remote_process` without that mode continues to use legacy NativeProcessRegistry. A/B grants, signed Agent command checks, platform hard-deny and per-owner capabilities still run before launch. Exact `operationId` write-ahead journal reserve **precedes** systemd-run side effects; logged job `processId` is stable across Supervisor restart. Same owner/job retry must not launch twice.
- `lib/supervisor-job-journal.mjs` stores only `backend='isolated-user-unit'` and strictly validated generated unit name along with existing owner fingerprint and processId; **no script or stdout stored in the central/local operation journal**. Process output/status are separately stored in private per-worker files. Journal is for locally protecting launch replays, not a substitute for relational PostgreSQL job orchestration.
- Official `client/core-files.json` includes the worker and manager modules: **87 files** staged and verified with digest parity. Windows/macOS installation and production are not touched.

## Security and rollback
- Worker flag is strictly scoped to a privately owned `gold-uat` user-manager bus and private persistent job directories. No root/systemd system-manager command is exposed to the remote Agent. Unit name/path is generated and regex-validated, no user-supplied OS PID kill.
- Per-job user unit is an **independent cgroup**; Supervisor restart and operator session close do not stop it. Explicit Stop uses `systemctl --user stop` on exactly that generated unit; force uses a targeted SIGKILL on that unit. Workers do not bind network ports of their own beyond what approved user script needs.
- If Supervisor, user manager, or filesystem evidence cannot prove the worker is alive or terminal, return `UNKNOWN`, never fabricate success, never relaunch the same operationId.
- To rollback UAT, first list and terminate only owned isolated test workers; disable `LIGHT_REMOTE_PROCESS_SUPERVISOR_ISOLATED_WORKERS` drop-in; restart isolated Supervisor; preserve journal and worker receipts; revert candidate source using recorded `90-g3-candidate.conf` and original full backup. Linger enablement may be reversed on isolated UAT only after confirming no user workers/services depend on it.

### Still unimplemented / risk boundaries
- **Machine reboot** with running job: systemd transient user units do not carry a verified restart-and-resume contract; do **not** auto-relaunch unknown jobs. Need OS resource lease/boot reconciliation and a persistence design validated separately.
- **Windows/macOS** dedicated isolated workers and installer/service orchestration are not available. Passing Windows/macOS CI only shows existing package builds have not regressed.
- The new isolated backend intentionally supports **noninteractive background exec only**, not durable interactive stdin. Outgoing stdout/stderr is capped at **4 MiB per stream** on disk with reported truncation; full build logs/progress percentage is another feature. Private command request is removed after worker opens it; journal contains no script/secret.
- Active Free/Pro/Pro Team execution slot Scheduler, M4 resource locking, centralized PostgreSQL relational job records/Redis queue, Fleet Wall Job Manager and owner Team call quota remain outstanding. Cross-account Team dispatch OFF. No client-wide release or production cutover.

**Rollback:** First inspect owner-managed user units `lr-m5w-*.service` and do not interrupt genuine user work. Disable only Gold UAT Supervisor `96-m5-isolated-workers.conf`, reload systemd, restart Supervisor, check local Wall/Operator readiness; preserve worker receipt files and prior journal. Source reversion uses verified candidate override snapshot and full backup. Linger may be disabled only if no other `gold-uat` user services need it. No production changes are authorized by this UAT.
