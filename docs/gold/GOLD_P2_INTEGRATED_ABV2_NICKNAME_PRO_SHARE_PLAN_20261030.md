## 4. A/B V2 exact product protocol
1. **OWNER CLARIFICATION 2026-10-30: always show the stable six-character prefix.** Wall in STANDBY visibly shows the permanent server-assigned device Short ID (e.g. `ABCD02`); authorized `/account` device rows and device-selection results may show the same public Short ID at all times, including offline/no pending request. This is the **fixed first six characters of V2 A**, not the complete one-time A code. Do **not** mint, show, count down, auto-refresh or rotate the **five-character suffix** in STANDBY. When exactly one Agent-initiated request is pending, show the *same fixed prefix* joined with its fresh suffix (e.g. `ABCD02-GHFDX`) and the request countdown; after approval/deny/expiry revert to only `ABCD02` in STANDBY. Device UUID remains authoritative; reserve immutable 6-char Crockford Base32 ID in PG17, uniqueness/collision retry, never recycle tombstoned ID. The public prefix is a nonsecret identifier, NOT an access code or authorization; account-scoped visibility rules still apply.
2. Owner or guest says e.g. "connect VPS-ARM / ABCD02 / Windows / THISPC". OAuth-scoped resolver shows ONLY permitted devices: owner-owned for owner, expressly shared owner devices for an invited guest. Return 0/1/N with count and at most 5 safe choices. Duplicate THISPC or 38 Windows matches require selection; never auto-pick Main or mint pending requests on ambiguous targets. Metadata discovery is not A/B authorization.
3. On exactly one online permitted target, helper initiates backend-bound request with A `6 short ID + 5 rotating characters` created ON DEMAND, independent B `4+4`, and one fixed pending-approval lifetime of **300 seconds (5 minutes)** from trusted server-side creation; both A's 5-character suffix and independent B expire together, with no extension on helper polling, reconnect, page reload or failed entry. This replaces the former 180-second V2 design default, **NOT** legacy V1's running default of 180 seconds. Both bound to account/client Agent/owner device/connection/request/grant scope, stored atomically with nonce/replay/rate controls. Agent sees **B plus verified target details**; no need to copy A from Wall.
4. Target Wall or owner-authenticated `/account` shows pending A, countdown, requester and **masked B indicator, never B plaintext in DOM/HTML/API**. Owner pastes B, verifies device and request, Approve/Deny; CSRF, owner account/device constraints and constant-time code verification required.
5. After approval helper resumes the **exact pending request** without reusing one-time A or exposing continuation secrets; grant/session creation uses existing governed mechanisms, 24h A/B lease, policies and separate session expiry. Race/retry idempotent; 2 Agent conversations / tabs / devices cannot hijack "newest" pending.
6. If expired/cancelled/denied/revoked/offline/connection ID changed, refuse and invalidate; legacy 4+4 A→B remains under compatibility flag on older Windows/macOS/Linux/plugin clients. No silent fallback to a different target.

## 12. OWNER ARCHITECTURE DECISION — leave a first-class expansion path for Light Remote IT Support (2026-10-30)

**Rationale:** A/B V2 is not only a UX shortcut. It is the future **target discovery + device-scoped approval + governed session** entry point for a dedicated Light Remote IT Support product. Design the current A/B V2 and Pro Share path so a future support organization can manage **device clusters, geographical/organizational branches, individual authorized users, and identity/permission groups**. This is an architectural forward-compatibility requirement for P2-I1/I2, **NOT approval to build the IT Support organization product or broad RBAC now**.

### Future distinct resource/identity axes — do not collapse or overload
- **Device**: authoritative immutable device UUID and stable public six-character Short ID. Short ID remains a device reference, **never embed organization/branch/group/user codes in it**; moving a device between branches does not change it. Prevent reuse after deletion/re-enrollment. Tenant-scoped visibility always checked, even when the identifier is known.
- **Organization / tenant** (future): trust and administrative isolation boundary; separate a device's `ownerAccountId` / owning organization, its `managedBy` context, the current `actorAccountId`, and a billed principal. Pro Share owner is not equivalent to an organization or global administrator.
- **Branch / site** (future): location/operational assignment and reporting, possibly hierarchical. A device may move between sites without changing ID, enrollment keys, A/B grant identity, or creating a new device.
- **Cluster / device collection** (future): logical selection of devices by purpose, environment, project or fleet. May be many-to-many; do not assume one cluster per device, or reuse a site identifier as a cluster.
- **User and group** (future): identities, memberships and explicit device/branch/cluster assignments. A user may belong to multiple groups; group name is never an authority token and group assignment alone never grants an A/B bypass. An IT Support Agent is an authenticated actor, not automatically an owner.
- **Permission grant / approval delegation** (future): records **who may discover, who may request access, who may approve B, and what capabilities they may execute**, with explicit scope, time, actor, device and policy revision. Approval delegation must be a deliberate, auditable owner/org policy, not inferred from an OS, branch or plan.

### P2-now extension seams (required in source contracts)
1. **Resolver interface**: resolve target by the **authenticated principal's permitted device set**, then match Short ID/hostname/alias/OS within it. Design a policy/query interface that can later intersect organization, branch, collection, individual user assignment and group assignment; today its only grant sources are owner-owned devices and explicitly shared Pro Share devices. Do not bake `device.ownerAccountId === actorAccountId` as the only possible authorized lookup. Never skip authorization or leak unassigned devices when broader filters are added.
2. **Request/authorization context**: canonical A/B pending record and audit must preserve immutable `deviceId`, `deviceOwnerAccountId`, trusted `actorAccountId`, `agentId/clientId`, `connectionId`, request/grant ID, approval actor, time and requested capability/scope. Leave optional future policy fields (`tenantId`, `siteId`, `collectionId`, `assignmentId`, `policyVersion`), validated and nullable at P2; **never use untrusted client-supplied fields to choose a tenant, approver, payee or device**.
3. **Separate policy decisions**: do not fuse `discover`, `request`, `approve`, `session`, `execute`, `bill` into one owner check. A reusable deny-by-default authorization service boundary can answer `list_visible_devices`, `request_device_access`, `approve_device_access`, `execute_on_device`; today use only strictly limited owner/guest policies. Grant state must be reevaluated at approval, session bind, queued job dispatch and sensitive actions; stale group/branch membership must not resurrect rights.
4. **Device ownership versus placement**: branch/cluster/group moves are metadata/assignment mutations, never re-enrollment or Short ID rotation; invalidate or fence pending/active access when a move **removes** effective permission. Recheck exact device UUID + connection ID and signed enrolled identity before executing.
5. **Wall and /account**: show stable Short ID regardless of pending request. Keep a device-scoped approval UI and server API that can later list/filter authorized pending requests by branch/cluster/group, without batch-approving an unrelated device. B remains independent and entered only by an explicitly authorized approver on the exact request. Current P2 still requires owner approval; future support approvers need separately explicit delegation.
6. **Pro Share as smallest scoped sharing policy**: implement 1 owner + 1 guest as a **constrained assignment**, rather than a special unconditional cross-account exception. Future IT Support can use the same resolver/approval/session audit contracts, but must have **separate tenant/RBAC/billing product entitlements**; do not auto-expand Pro Share into a support organization or revive the frozen 5-seat Team SKU.
7. **Backend/persistence**: PG17 durable canonical IDs and assignments, Redis8 only TTL/CAS/leases. Migrations after 042 are additive; avoid prematurely creating organization/group/branch tables, fake roles, broad public enumeration, inherited approval or paid IT Support SKU. Use typed/optional scope fields and isolated policy adapters so actual future tables can attach without breaking current A/B V2 API.
8. **Compatibility and audit**: keep existing legacy A/B 4+4, 24h grant, immutable sessionId, device policy and native signed execution proof. Every access/revocation and resulting remote operation must be attributable to an authenticated person/Agent and exact device, including what scope authorized it.

### Scoped RBAC plus device-attribute/policy evaluation
This example requires **role + scope binding**, not a flat enum `admin|user`. An extensible policy evaluator takes: authenticated **actor** (and optionally groups), target **device** with organization and current branch, requested **action** (discover, request pairing, approve B, read, terminal, desktop, execute, manage assignment), active role/group/device assignments, expiry/revocation and approved device capabilities. Deny unless authorized by an explicit applicable binding. In the later IT Support product, effective grants may be direct per-user, via group, via branch, via named device collection, or org-wide. Evaluate union of explicit allow scopes subject to more restrictive device policy, explicit denies and tenant isolation; never infer permission from display name, Short ID or client-provided branch. Keep decision records/audit with the matched authoritative assignment/policy revision.

Illustrative logical data relationships (not executable migrations or a demand to create all tables now):
`Organization → Branch (1:N)`; `Organization → Device (1:N)`;
`Device → currentBranch (0..1)`; `Device ↔ Cluster (N:M)`;
`User ↔ Group (N:M)`; `Principal/Group ↔ ScopeBinding(role, organization/branch/cluster/device, actions, expiry)`.
IT Leader's org-scoped role covers all branches automatically; each support engineer's role covers only their two assigned branches. A group may contain users covering different or overlapping scopes, and a person can have additional direct-device exceptions. Group membership is **not** an A/B approval credential.

### Required transfer / reassignment semantics
1. **Move device from B01 to B03 within same company:** its UUID, enrolled device identity, stable six-character Short ID and history remain unchanged. After a transactional branch-assignment update, S01 loses effective device discovery and new pairing/execution access while S02 gains **eligibility** to discover/request. S02 DOES NOT inherit S01's prior A/B approval or sessions; owner/delegated approver must approve B for S02's own Agent. Leader A retains org-wide scope.
2. **Change S03 assignment from B05+B06 to B05+B08:** revoke permissions inherited through B06 immediately and add eligibility for B08 only. Apply the change to all devices in the branch without manually relabeling 10 individual device grants. Previously authorized sessions/jobs must recheck current scope; newly forbidden queued work is fenced, in-flight effects retain honest unknown/terminal accounting and are not falsely ACKed or killed by database changes alone.
3. **Move a device to another support group, cluster, or direct user:** evaluate effective permissions based on each independent assignment. Do not mutate its immutable ID. Explicit one-device exception does not accidentally grant the entire branch; moving a cluster tag is not changing ownership.
4. **Transfer between separate organizations/tenants:** different from moving branches. Require authorized release/acceptance, revoke old organization grants, enforce tenant isolation, re-evaluate enrollment trust and potentially re-enroll according to ownership-transfer policy; NEVER automatically carry over old company approvals/credentials or billing identity.

### UX and future APIs, without overbuilding P2
- Leader's IT Support console may choose `All company devices` or drill down **Branch → Group/Cluster → Device**, and reassign branch or responsible support user with audit. The five support consoles show their permitted two branches only; inaccessible branch names, device counts and Short IDs must not leak.
- Existing Gold A/B V2 Helper resolves `connect branch B03 device ABCD02` only within the actor's authorized set; it must never create a pairing request from a mere group/branch hint without exact device resolution. Show at most five matches by default.
- A/B pending request stores canonical device UUID, requester, approver, source organization/branch and **policy version** as authoritative server-derived context. On a device move or assignment revoke while pending, **revalidate before approval**; stale pending requests fail closed and are cancelled instead of approving a previous access scope.
- Session display nickname and Pro Share guest membership do not change any of these device ownership/assignment semantics. Keep these future scope constructs composable rather than embedding Pro Share billing into IT Support group roles.

### Post-stabilization IT Support scenario — future reference only, not a P2 release test
Fixture: 10 branches, 100 devices, 5 support actors, one Leader, overlapping cluster/group bindings, plus an unrelated second organization. Assert: Leader sees 100; each Support initially sees only its assigned ~20; targeted Short ID resolves only when in scope; move one device B01→B03 and assert Leader still sees 100, S01 loses one and S02 gains one, both with unchanged device UUID/Short ID; S02 has **no inherited grant**; revoke an entire branch assignment and assert forbidden in-flight revalidation / queued-work fencing; move a cluster without crossing tenant; cross-organization enumeration denied; no self-approval by claiming leader/group fields in the request. Use this scenario to **validate P2's policy abstraction seam**, not to claim future enterprise management UI/RBAC is deployed.

For **current Gold P2**, implement only the generic server-derived policy context and scoped resolver seams required by owner-owned and Pro Share-shared devices. All organization/branch/group CRUD, complex inheritance, enterprise user onboarding, delegated approver management and a full IT Support management console remain for a separate Light Remote IT Support product. The enterprise scenario must not expand current scope or delay security gates by attempting to implement the whole enterprise system now.

## 14. A/B V2 recovery and manual Refresh — preserve V1 troubleshooting UX (2026-10-30)

**Owner UX requirement:** existing V1 Wall Refresh creates a fresh A when an Agent cannot redeem the displayed code, pairing state/clock display is stale, or a connection was interrupted. A/B V2 MUST provide an equivalent recovery path and must not trap an owner when Agent-initiated device discovery is broken. This is a **design contract, not yet implemented**.

**STANDBY (no pending Agent request):** Always show the immutable six-character public Short ID with **Refresh device connection/status** (re-query trusted server presence/registration, no new code and no changed Short ID), **Copy Device ID**, and a deliberate **Manual pairing (legacy A/B V1)** escape hatch for when the V2 resolver/Agent cannot start a request. Manual pairing uses the existing owner-approved V1 4+4 A code, one-use semantics and 3-minute TTL, never silently bypasses A/B, and may be hidden once a future equivalent recovery design is validated. A successful status refresh alone grants no session or execution. If backend is unreachable, show an explicit offline/not-synced state; the Wall cannot locally mint valid backend A/B credentials.

**PENDING (exact Agent-initiated V2 request):** Wall and authenticated `/account` offer **Generate new code / Refresh request** for the selected pending request only. Under the verified owner/session and CSRF protection, perform an **atomic compare-and-swap** on `requestId` + `attemptId` + current connection/policy: invalidate the old V2 five-character A suffix **and** old independently generated B (including old hashes), mint new cryptographically independent A suffix and B, advance `attemptId`/generation, set a **fresh maximum 300-second absolute server deadline** for that *explicit* refresh. Short ID and device UUID remain unchanged. Do NOT re-open a denied, approved, expired or revoked request silently; those require Agent to start a new exact request. Do NOT rotate other simultaneous Agents' pending requests.

**Agent synchronization:** `light_remote_connection_helper` resume/poll is bound to the *same* authenticated Agent/client, account, device and `requestId`. If the owner explicitly refreshes while the Agent is waiting, its next authorized helper poll returns **the new B only to that Agent** and clearly marks the previous B obsolete. B is never sent as plaintext to Wall, `/account` or a different Agent. Agent/Wall status changes are versioned; stale approval and old helper continuations cannot approve or resume the new generation. If the Agent connection is gone, instruct the user to retry its same helper call; do not report ready until a verified new code/approval exists.

**TTL and abuse resistance:** Distinguish **manual refresh** (explicitly creates a new attempt, 300 seconds) from implicit operations: helper retry, page reload, reconnect, repeated polling, countdown display, or failed B input must NEVER extend TTL. Apply per-account/device/Agent/IP bounded refresh+issuance limits, brief cooldown and audit `requestId/attemptId`, and clear error/try-again guidance. Time validation is entirely authoritative **server UTC**; client-side countdown is display-only and clock skew must not permit late approval. Connection ID change, lost enrollment trust, owner revocation, denied request, or target becoming unauthorized invalidates the pending request.

**Acceptance examples:** (1) Agent V2 cannot find device → Wall refreshes status and shows permanent Short ID; authorized owner can initiate legacy manual V1 without switching identities. (2) Pending V2 A/B mismatch → owner explicitly refreshes selected request; previous A/B immediately denied, Agent polls exact request and sees fresh B; no new owner approval inferred. (3) After 300s, approval denied by server clock even if Wall countdown is wrong. (4) Refresh one of two Agent requests only changes that request. (5) Replay, wrong account, wrong approver, unavailable backend, revoked device, excessive refreshes, and pending request races fail closed. (6) Approved A/B grant still expires at hard 24h; V1 3-minute TTL unaffected.

**P2 test requirement:** add these to A03/A04 and M1 before the single integrated candidate freeze, with native Wall and browser verification after feature implementation. Do not implement future enterprise IT Support hierarchy or RBAC to support this.
